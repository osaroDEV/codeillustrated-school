# Database & auth

Supabase config (`config.toml`), email templates (`templates/`) and SQL migrations (`migrations/`, applied in filename order). The Supabase CLI is a dev dependency, so run it with `pnpm exec supabase …` or the `db:*` scripts.

These migrations cover Phases 1–7 of the LMS, plus editable course addresses and the contact inbox. The later phases are planned in [`docs/lms-roadmap.md`](../docs/lms-roadmap.md).

| Migration | What it does |
| --- | --- |
| `…000000_baseline.sql` | The original hand-made tables (`profiles`, `invite_codes`, `enrollments`, `announcements`, `learner_notes`). Guarded with `if not exists`, so it does nothing on an existing database. |
| `…000100_roles_and_rls.sql` | `profiles.role` / `profiles.email`, the `is_admin()` helper, a trigger that creates a profile on signup, and RLS policies on the existing tables. |
| `…000200_course_catalogue.sql` | `courses`, `course_modules`, `lessons`, `offerings`: anyone can read, only admins can write. |
| `…000300_seed_courses.sql` | Seeds the catalogue from `lib/course-catalog.ts`, generated by `node scripts/generate-course-seed.mjs`. |
| `…000400_require_email_verification.sql` | Makes every existing account that was never sent a verification email unverified again, and ends its sessions. |
| `…000500_unique_enrollments.sql` | Merges duplicate enrollments (keeps the row with the most progress and appends the notes from the others), then adds `unique (user_id, course_id)`. |
| `20261104000000_cohorts_and_sessions.sql` | Phase 2. Adds the `instructor` role, `cohorts`, `class_sessions` and `attendance`, and `enrollments.cohort_id`. A trigger refuses placements in a full cohort or a cohort of a different course. Links `enrollments.course_id` to `courses`. Adds the reorder functions used by the course editor. Stops anon and signed-in clients from reading `lessons.content`, `video_url` and `file_path`. |
| `20261105000000_billing.sql` | Phase 3. Monthly billing for cohort seats: `payment_plans`, `subscriptions`, `orders`, `payment_events`, plus `enrollments.source` and `subscription_id`. The billing functions `fulfil_subscription_order`, `record_renewal`, `expire_subscriptions` and `mark_order_refunded` can only be called with the service role. |
| `20261106000000_course_slugs.sql` | Editable course web addresses. `courses.id` stays the permanent internal ID that everything else points at; the public address comes from the new `courses.slug`. A trigger records each address a course leaves in `course_slug_redirects`, so old links redirect to the new page. Anyone can read redirects for published courses; only the trigger writes them. |
| `20261108000000_contact_messages.sql` | Keeps messages from the public contact forms for Admin → Messages. Only `/api/contact` (service role) writes them; only admins can read them. |
| `20261109000000_lessons_and_progress.sql` | Phase 4. `lesson_progress`, `course_resources` and the private `course-files` bucket. Triggers recalculate `enrollments.progress` from completed lessons and attendance; earlier hand-set values are kept in `progress_baseline` as a starting credit. |
| `20261110000000_lesson_blocks.sql` | A lesson becomes an ordered list of `lesson_blocks` (text, video or file) and existing lesson material is carried over. Only server code reads blocks, after the access check. `lessons.content`, `video_url` and `file_path` are no longer read. |
| `20261111000000_self_paced.sql` | Phase 5. Self-paced subscriptions per course: optional yearly prices on `offerings`, yearly payment plans, and billing functions that extend each period by the plan's interval. |
| `20261112000000_shared_recordings.sql` | Adds `class_sessions.shared_with_self_paced`, off by default. Self-paced subscribers only see recordings an admin has shared. |
| `20261113000000_assessments_and_certificates.sql` | Phase 6. Quiz and assignment blocks, `quiz_attempts`, `assignment_submissions`, the course completion rule and `certificates`. Saving a lesson now keeps block IDs, so learner work stays attached. |
| `20261114000000_notifications_and_replies.sql` | Phase 7. `email_outbox`, the course-email preference on `profiles`, replies on learner notes, and the token Supabase's scheduler uses. After applying it to production, run `supabase/sql/schedule-notifications.sql` once there to start the 15-minute job. |

## Local development

Needs Docker Desktop.

```sh
pnpm db:start      # starts Postgres, Auth, Studio and Mailpit; prints the local URL and keys
pnpm db:reset      # re-applies every migration from scratch
```

Put the printed API URL, anon key and service-role key into `.env.local`. Verification emails are captured by Mailpit at http://localhost:54324 instead of being sent.

`pnpm test` also applies every migration to an in-memory Postgres (PGlite) and checks the triggers and RLS policies (`tests/db/migrations.test.ts`), so SQL mistakes are caught without Docker. It doesn't exercise PostgREST or Supabase Auth.

## Email verification

Every account must click an emailed link before it can sign in:

- **Signup** goes through `supabase.auth.signUp`, which sends the link.
- The link is built from `templates/confirmation.html` and points at `/auth/confirm`, which verifies it and signs the learner in.
- **Accounts created before this change** are reset to unverified by migration `…000400`. Learners get a new link from the login page ("Resend verification link"), from `/auth/verify-email`, or from the admin panel's **Email verification links to all unverified** button.

## Rolling out to the hosted project

1. **Configure auth on the hosted project** in Dashboard → Authentication. Don't use `supabase config push`: it would copy the local `localhost` site URL from `config.toml` onto the hosted project.
   - Turn on "Confirm email".
   - Site URL: `https://codeillustrated.com/academy`. Add `https://codeillustrated.com/academy/auth/confirm` to the redirect URLs.
   - Set up custom SMTP first (Brevo: `smtp-relay.brevo.com:587`, using your Brevo SMTP login and key). Supabase's built-in mailer only sends to project team members, and free-plan projects can't edit email templates until custom SMTP is on.
   - Set the "Confirm signup" template to the contents of `templates/confirmation.html`. If you skip this, the default link still verifies the account, but `/auth/confirm` can't sign the learner in, so they're sent to the login page instead.
   - Set the "Reset password" template to the contents of `templates/recovery.html`. Its link signs the learner in through `/auth/confirm` and opens `/auth/reset-password`; the default template's link can't, so "Forgot password?" wouldn't work without it.
   - Raise Rate Limits → "emails sent per hour" from the default (2) to something like 30.
2. **Apply the migrations before the code that needs them is deployed**, so before merging to `main`. The migrations only add things, so the code already live keeps working. If you deploy first, the live site queries tables that don't exist yet; that happened with Phase 2. To push to production without re-linking the CLI away from staging, run `pnpm exec supabase db push --linked --project-ref <production ref>`. Add `--dry-run` first to see what it will apply.
3. **Deploy the code** by merging to `main`.
4. **Promote yourself to admin** in the SQL editor:
   ```sql
   update public.profiles set role = 'admin' where email = 'you@example.com';
   ```
5. **Verify your own email:** sign in, click "Resend verification link" and follow the link. Admins have to verify too.
6. **Send everyone else their links** from Admin → Learners → **Email verification links to all unverified**.

## Payments (Phase 3)

Cohort seats are monthly card subscriptions through Flutterwave (v3 API). To turn them on:

1. **Flutterwave dashboard** → Settings → API keys: copy the secret key. Use test keys on staging.
2. **Settings → Webhooks:**
   - URL: `https://codeillustrated.com/academy/api/payments/flutterwave/webhook`
   - Secret hash: a long random string.
   - Make sure v3 webhooks and "retry on failure" are on, and enable the charge and subscription-cancellation events.
3. **Vercel env vars:**
   - `FLW_SECRET_KEY` and `FLW_SECRET_HASH` (the same hash as step 2).
   - `CRON_SECRET` (any long random string; Vercel Cron sends it to `/api/cron/billing` every day at 06:00 UTC).
   - `BREVO_API_KEY` (already set for the newsletter) for receipts. `RECEIPT_FROM_EMAIL` must be a sender verified in Brevo and defaults to `info@codeillustrated.com`.
   - Optional: `APP_URL`, the base used for the Flutterwave redirect. It defaults to `https://codeillustrated.com/academy`. Set it per environment, e.g. `http://localhost:3000/academy` locally or the staging URL.
4. **Prices:** in Admin → Courses, set the group and 1-on-1 prices (monthly, in USD and NGN) and tick "On sale". Only offerings that are on sale and priced in both currencies show a Subscribe button.

Refunds are made in the Flutterwave dashboard; Admin → Payments → "Mark refunded" only records them. Charges the webhook couldn't match to a subscription show under Admin → Payments → Needs attention.

**Instructors** (Phase 2): an admin gives someone the instructor role from Admin → Learners → Role, then assigns them to a cohort. Instructors sign in as usual and get a **Teaching** link in their dashboard. It shows only their own cohorts, where they can mark attendance and add meeting and recording links.

`ADMIN_SECRET` is no longer used. Until the catalogue migrations are applied, the site serves the bundled `STATIC_COURSES` (see `lib/courses.ts`).

## Staging

`academy-staging` (`gvngucukipythqmtsqyb`) is a separate free project for testing; it holds no real data. The CLI is linked to it (`supabase/.temp`, git-ignored), so `pnpm db:push` targets staging. Run `supabase link --project-ref <ref>` before pushing anywhere else.

- To run the app against staging, put its URL, anon key and service-role key in `.env.local`, which overrides `.env`.
- Its SMTP points at an Ethereal test mailbox (`smtp.ethereal.email`), which catches every email and delivers none.
- Its Site URL is `http://localhost:3000/academy`, so verification links point at a local dev server on port 3000.
